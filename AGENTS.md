# Repository instructions for coding agents

## Product

This repository contains a Telegram-first AI marketing copilot for marketers, experts, and small businesses.
The product should do marketing work, preserve brand context, and explain the reasoning behind recommendations.

The MVP product flow is:

`competitor analysis -> commercial creative package -> mentor explanation`

See `docs/product/mvp-functional-scope.md` and `ARCHITECTURE.md` before architectural work.

## Required workflow

- Never implement feature work directly on `master`.
- Use `sale-ready` as the integration branch and a dedicated task branch for each change.
- One OpenSpec change should map to one reviewable branch/PR unless the approved design explicitly splits delivery into phases.
- Before implementation, read the active OpenSpec change under `openspec/changes/<change>/`.
- Do not implement behavior outside the active change.
- If a requested behavior is not specified clearly enough to implement safely, update the OpenSpec artifacts before changing runtime code.
- Use conventional commit messages such as `feat(scope): subject`, `fix(scope): subject`, `refactor(scope): subject`, `docs(scope): subject`.

## OpenSpec

`openspec/specs/` describes current behavior.
`openspec/changes/` describes proposed behavior changes.
`openspec/config.yaml` contains shared project context and artifact rules.

For new features, architecture changes, queue/reliability changes, migrations, or public contract changes:

1. explore the problem;
2. create/review the OpenSpec proposal, delta specs, design, and tasks;
3. implement only after the artifacts are ready;
4. run verification;
5. archive/sync the change after the implementation is accepted.

Codex OpenSpec skills are generated by the OpenSpec CLI. Do not hand-edit generated `.codex/skills/openspec-*` files. If they are missing or stale, run `openspec init --tools codex --profile core` or `openspec update` from the repository root.

## Architecture invariants

- FastAPI routers stay thin: HTTP binding, dependency injection, basic HTTP errors, delegation.
- Telegram handlers stay thin: Telegram UX, payload mapping, rendering, delegation.
- Business logic belongs in services/domain layers.
- Do not call OpenAI directly from Telegram handlers or HTTP routers.
- PostgreSQL is the durable source of truth for users, tasks, conversations, brand profiles, and future workflow/job state.
- Redis, when introduced, is transport/coordination infrastructure, not the canonical business store.
- `BrandProfile` is durable brand context. Conversation facts are temporary chat context.
- `TaskPipelineService` remains the single-task execution pipeline. Future multi-step product workflows belong in a separate workflow layer rather than expanding the task router into a monolith.
- Reuse `UrlAnalyzer` and `ImageOrchestrator` instead of creating parallel scraping/image stacks without an approved design reason.
- Preserve existing `/chat`, `/tasks`, `/images`, and `/brand-profile` contracts unless the active OpenSpec change explicitly modifies them.

## Database and migrations

- Never edit an already merged migration.
- Every schema change requires a new Alembic migration from the current head.
- Keep SQLAlchemy models, constraints, indexes, and migrations consistent.
- Keep transaction ownership explicit in service design.

## Testing and verification

Every behavior change requires tests.
Bug fixes require a regression test when practical.
Do not make real OpenAI calls in unit tests.
Do not require Telegram polling in unit tests.
Mock/fake external HTTP and model calls unless an integration test explicitly owns them.

Before marking work complete, run the checks relevant to the change. Baseline checks are:

```bash
pytest
python -m compileall app bot
```

For schema changes also run:

```bash
alembic upgrade head
```

For OpenSpec changes also run:

```bash
openspec validate --all --strict
```

Never claim a command or test passed unless it was actually executed successfully.

## Completion report

When finishing a coding task, report:

- files changed;
- behavior implemented;
- migrations added;
- commands actually run;
- tests/checks that actually passed;
- remaining limitations or blockers;
- manual verification steps when relevant.

Do not silently refactor unrelated code, rename public fields, replace dependencies, or widen the scope of a change.
