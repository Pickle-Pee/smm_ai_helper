# Database migrations

Проект использует Alembic для управления схемой БД.

## Новая пустая БД

```bash
alembic upgrade head
```

После этого можно запускать backend.

## Уже существующая MVP-БД

Для БД с Alembic history остановите/дождитесь завершения запросов backend, проверьте `alembic current`, примените `alembic upgrade head`, затем выполните `alembic check` и запустите совместимую версию приложения. Текущая новая миграция `20260909_0008` добавляет standalone finalization token/lease. Старые процессы не соблюдают новые claims, поэтому смешанный rollout не сохраняет гарантию защиты от повторного исполнения.

Если таблицы созданы старым `Base.metadata.create_all` без Alembic history, сначала сравните фактическую схему с конкретной ревизией. `stamp` не создаёт столбцы, индексы и constraints. Нельзя помечать произвольную существующую БД как `head`: так новые migration steps будут пропущены.

Только для схемы, которая проверенно соответствует первоначальной baseline `20260707_0001`, применим такой переход:

```bash
alembic stamp 20260707_0001
alembic upgrade head
alembic check
```

Если схема не соответствует известной ревизии, требуется отдельная сверка/корректирующая миграция; не подбирайте stamp по предположению. Для следующих изменений используйте:

```bash
alembic upgrade head
```

## Важно

Backend больше не создает таблицы автоматически на startup. Это сделано намеренно, чтобы изменения схемы были явными и контролируемыми.

Миграция `20260909_0008` сохраняет существующие ответы сессий, canonical completed responses и Task history; downgrade удаляет только claim columns/constraints и теряет сведения об активном владельце. Downgrade выполняется с остановленными backend-процессами. Подробный контракт: [standalone tasks](task_pipeline.md).

Тестовые downgrade/re-upgrade выполняются только на отдельных disposable PostgreSQL databases из README, никогда на общей БД с пользовательскими данными. Уже объединённые миграции не редактируются.
