# Fixed Telegram marketing workflow

The implementation keeps Registry 1.0.0 metadata-only with zero execution bindings and the generic deterministic planner `PLANNING_ONLY`. Three explicit executors in the workflow layer use ExpertInstructionComposer and structured output schemas. The `app/workflows/quality.py` Quality Gates adapter checks typed claims, evidence and lineage before artifact persistence; it does not establish semantic truth. The evaluator's Registry-derived readiness remains `PLANNING_ONLY`; its structural gate outcomes and eligibility manifest are usable by the explicit fixed workflow without enabling generic execution.

PostgreSQL owns MarketingRun, MarketingArtifact, Job, execution leases and delivery state. A small Redis list carries job ID wakeups. Every worker also scans the indexed durable execution records, so commit/publication crashes, duplicate messages and complete Redis loss cannot lose work. This is deliberately a fixed three-step workflow, not a general queue framework.

One run per actor/request key and one job per run/step are created under short owner/run row locks. Workers claim due executions with SKIP LOCKED. Each attempt receives a random fencing token and a lease longer than the execution timeout. No database transaction remains open during URL, model, image or Telegram calls. Expired leases can be reclaimed; stale workers cannot complete a newer attempt. Transient failures use bounded retry/backoff, while invalid output and unsupported input terminate clearly.

Artifact, Job outcome, Run transition and delivery parts commit together. Telegram delivery has its own leases, retries and acknowledgements, and never reruns generation. A send accepted by Telegram immediately before acknowledgement is lost can be delivered twice: neither model calls nor Telegram sends have exactly-once semantics. Local completion is idempotent. Lease recovery after ambiguous provider timeout may repeat a charged call.

Inputs snapshot the brand, requested goal and source evidence. Creative uses the saved analysis; mentor uses the saved analysis and creative only after an explicit user action. Updating BrandProfile does not change an existing run's explanation context. PNGs use a shared durable backend/worker media volume, and artifact payloads retain image IDs scoped to the owner.

The MVP supports private Telegram chats. It does not implement generic Orchestrator execution, arbitrary 15-module execution, autonomous replanning, generic synthesis, campaign execution, CRM integration, final video generation/editing or production deployment.

Standalone `/tasks/start` and `/tasks/answer` remain in TaskPipelineService. They use a separate PostgreSQL finalization claim and canonical response/history transaction, require no Redis and do not enter this workflow. See [standalone claim and replay contract](../task_pipeline.md).

## HTTP contract

All `/workflows` endpoints require `Authorization: Bearer BOT_BACKEND_TOKEN` and positive int64 `X-Telegram-User-ID`. The header is a trusted bot assertion, not a public end-user authentication mechanism. Every lookup joins the run to its owning User; a foreign run/job/artifact returns 404. Callback handlers use the pressing user's ID.

| Endpoint | Purpose |
| --- | --- |
| `POST /workflows` (202) | `marketing_request.v1`: `request_key`, `competitor_url`, optional `product`, `audience`, `goal`; persist quickly |
| `PUT /workflows/profile` | Explicit durable BrandProfile update; no conversation facts are promoted |
| `PATCH /workflows/{run_id}/context` (202) | Supply missing business fields before work begins |
| `POST /workflows/{run_id}/continue` (202) | `action=creative` or `mentor`; existing step is reused |
| `GET /workflows` | Last ten runs belonging to the actor |
| `GET /workflows/{run_id}` | Status, saved artifacts, jobs, delivery and sanitized errors |
| `GET /workflows/{run_id}/artifacts/{step}` | Saved typed result, evidence, assumptions, limitations, input snapshot, claim IDs, Quality Gates outcome and lineage hashes |
| `GET /workflows/{run_id}/jobs/{job_id}` | Owned step status |
| `POST /workflows/{run_id}/delivery/retry` | Reset failed sends only; retain delivered parts and artifacts |

The trusted bot alone consumes `/internal/delivery/claim` and acknowledges `/internal/delivery/{id}/ack` with a random attempt token. No actor header is required for this service-wide worker function; the owner comes from the persisted run. Do not expose the service bearer credential to end users.

Input/output schemas are defined in `app/workflows/schemas.py`: analysis/creative/mentor inputs and results each carry their own v1 schema tag; persisted envelopes use `marketing_artifact.v1`. Initial explicit values override the profile for that run. Existing runs retain the profile snapshot captured at creation. After work starts context is immutable. Evidence IDs are generated by the executor; unknown references and invalid timelines fail validation. Confidence cannot exceed parent claims. Evidence snapshots and excerpts remain data, including any instructions embedded by a source.

## Attempts and delivery

Worker concurrency defaults to 2 (configurable 1–8). One attempt has a 240-second timeout and a 270-second lease by default; the lease always exceeds `WORKFLOW_TIMEOUT_SECONDS` by 30 seconds. A step permits at most three claims, including attempts interrupted by a process crash. Transient provider errors retry after 5 and 10 seconds. Unsupported URLs/insufficient source text and malformed structured results terminate with an actionable error. There is no automatic rerun of a failed terminal step: a new analysis message starts a new run.

Jobs retain the foundation lifecycle `pending -> running -> succeeded|failed`. Retrying an execution does not rewind this lifecycle; `JobExecution` owns attempts and availability. Duplicate Redis signals merely prompt a DB claim and cannot execute an already completed job. Every idle lane scans PostgreSQL approximately once per second; Redis recovery is not a prerequisite for recovering work.

Each text/image delivery part permits eight attempts with a 90-second lease and backoff capped at 300 seconds (Telegram's explicit retry-after can extend it). An expired sender cannot acknowledge a newer token. Parts of a job are delivered in order; a failed earlier part blocks later parts until `/redeliver`. Success acknowledgements store Telegram message IDs. Generation and delivery have separate recovery boundaries. The API and polling bot must remain running for automatic delivery; `/result` remains an on-demand recovery path.
