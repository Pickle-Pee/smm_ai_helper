# EXPERIMENTS: диагностика ReadError и бюджета времени графа

Статус: **диагностика, код и конфигурация не менялись** (15.11.2026).
Предложение по таймауту — в §5, решение за владельцем.

## 1. Как устроен вызов

- Один блокирующий POST в Responses API без стриминга (`app/llm/openai_text.py`), одна попытка
  (`single_attempt=True`). Пока модель генерирует, по соединению не приходит ни одного байта.
- `httpx.Timeout(HTTP_TIMEOUT)`: одно значение для connect/read/write/pool. Для запроса без стриминга
  read-таймаут фактически равен полному времени генерации.
- Транспортная ошибка или таймаут — это исход «unknown»: `retry_policy` останавливает узел
  (`stop_unknown_outcome`), повтора нет. Это правильно и не меняется.

## 2. Действующие лимиты (production, `release-e99f20f-20261114.json`)

| Параметр | Значение | Что ограничивает |
| --- | --- | --- |
| `HTTP_TIMEOUT` | 120 с | один POST к провайдеру (общий для всех текстовых и графических вызовов) |
| `GRAPH_TIMEOUT_SECONDS` | 300 с | один узел графа в worker; у POSITIONING в него входят генерация **и** верификация |
| `GRAPH_LEASE_SECONDS` | 330 с | аренда job; обязана быть больше таймаута узла |
| API `/copilot/execute` | 300 с | `asyncio.timeout(GRAPH_TIMEOUT_SECONDS)` |
| Telegram-бот | 310 с | ожидание ответа API; дальше пользователь нажимает «Проверить готовность» |

Инвариант конфигурации: `HTTP_TIMEOUT < GRAPH_TIMEOUT_SECONDS < GRAPH_LEASE_SECONDS`.
Общего дедлайна на весь граф нет, узлы идут последовательно.

## 3. Измерения

Источник: transport receipts live-harness и экспорт Telegram, 18 вызовов EXPERIMENTS с сохранёнными данными.

- 17 завершённых: 53,0 · 57,6 · 62,2 · 62,7 · 63,6 · 64,1 · 64,1 · 65,6 · 69,0 · 72,0 · 72,5 · 72,8 ·
  75,4 · 85,2 · 88,8 · **91,8** (Telegram, пекарня) · **112,8** с.
  Медиана 69 с; 4 из 17 дольше 85 с; максимум 112,8 с — это 94 % лимита в 120 с.
- 1 незавершённый: `httpx.ReadError` на 91,5 с (курс `a640c592…`, кандидат `100bff1`), без HTTP-статуса,
  `response_id` и usage. Исход неизвестен, вызов не повторялся и не извлекался.
- Выход: 6 383–7 905 токенов при бюджете 16 000; вход 30–36 тыс. токенов.
- Длительность не объясняется объёмом: 112,8 с при 6 451 токене и 53,0 с при 6 383.
  Скорость провайдера менялась от 57 до 125 токенов/с.

Остальные узлы (типично): Intent около 10 с, POSITIONING генерация 35–50 с, верификация 15–45 с,
CMO 36–46 с. Весь граф — 150–250 с; пекарня в Telegram — 193 с только на вызовы провайдера.

## 4. Выводы

1. **ReadError — не таймаут клиента.** При лимите 120 с таймаут дал бы `ReadTimeout` на 120-й секунде.
   Соединение разорвано со стороны сети или провайдера на 91,5 с.
2. **Жёсткого обрыва около 90 с нет:** более поздний вызов длился 112,8 с и завершился.
   По имеющимся данным это единичный транзиентный разрыв (1 из 18, около 6 %). Точную причину
   по сохранённым данным установить нельзя: harness не записывал тип нижележащей ошибки сокета.
3. **Риск растёт с длительностью.** Запрос без стриминга держит молчащее соединение 53–113 с;
   чем оно дольше, тем вероятнее и разрыв, и превышение лимита.
4. **Запас по `HTTP_TIMEOUT` мал.** Наблюдаемый максимум — 94 % лимита. Вызов дольше 120 с даст
   неизвестный исход, граф остановится после уже оплаченных POSITIONING и CMO.
5. **Бюджет узла сейчас выдерживается:** EXPERIMENTS — один POST (≤ 120 с < 300 с); POSITIONING —
   два POST, худший случай 240 с < 300 с.
6. **Ожидание в Telegram.** Граф на 190–250 с близок к окну бота в 310 с с учётом очереди и записи
   артефактов, поэтому ответ иногда приходит только по кнопке «Проверить готовность».

## 5. Предложение (не реализовано)

**А. Только конфигурация, рекомендую для ближайшего релиза.**
`HTTP_TIMEOUT` 120 → 180, `GRAPH_TIMEOUT_SECONDS` 300 → 420, `GRAPH_LEASE_SECONDS` 330 → 450.

- Одного `HTTP_TIMEOUT=180` недостаточно: у POSITIONING два POST в одном узле, худший случай
  360 с превысил бы таймаут узла в 300 с и оборвал бы верификацию с неизвестным исходом.
  Значения 420/450 сохраняют инвариант и укладываются в допустимые границы настроек (900/960).
- Запас по наблюдаемому максимуму становится 37 % вместо 6 %.
- Не устраняет разрывы соединения и не ускоряет ответ. `HTTP_TIMEOUT` общий, поэтому вырастет
  и предел ожидания для остальных вызовов провайдера.
- Окно бота (310 с) и API (300 с → 420 с вместе с `GRAPH_TIMEOUT_SECONDS`) нужно согласовать:
  иначе API будет ждать дольше бота. Это отдельная небольшая правка в `bot/copilot_client.py`.

**Б. Структурно, отдельным проектом.** Стриминг или фоновый режим Responses API с опросом по
`response_id`: молчащего соединения нет, разрыв перестаёт означать неизвестный исход. Затрагивает
durable receipts и учёт POST, поэтому требует отдельного проектирования и не входит в этап 1.

**В. Не рекомендую.** Уменьшать число экспериментов или бюджет вывода ради скорости: длительность
определяется скоростью провайдера, а не объёмом, и это изменило бы продуктовый контракт.

До решения владельца действует текущая конфигурация. В live-приёмке этапа 1 длительность каждого
вызова EXPERIMENTS фиксируется в журнале; вызов с неизвестным исходом не повторяется.
