# AUTH-01 · Email credentials and reversible account links

Backend baseline `b96771436eaf8eb304c31a36982e0a40da80bd55`. Web baseline `248f6e3d39f160cd958355da94fd45b452cb8363`. Product tracking: [SaaS Platform #158](https://github.com/Pickle-Pee/smm_ai_helper/issues/158).

## Identity and ownership

- A credential proves one existing or newly created `users.id`. Email login resolves the normalized, verified `external_identities(provider='email', subject=…)` row and its password credential. Telegram login continues to resolve the verified numeric Telegram identity through the bot boundary. The web session remains owned by the authenticating user and records its proof method before linking can be enabled. The caller never supplies its principal, a Telegram actor header, or a list of eligible sources.
- Display names, Telegram usernames and contact addresses provide no evidence of identity equivalence. Each channel resolves its current principal independently. A logical account consists of one principal or an explicitly verified pair, with stable source IDs and a versioned access grant. The linked viewer is the authenticated principal, plus a scoped grant for the supported source projections. Existing authentication and writes keep their effective author.
- With two existing principals, store a reversible bilateral link between the exact email and Telegram identities, with their original principal IDs. Enforce one active link per identity and per principal, and at most one current email/password credential per user. Serialize confirm and unlink by locking the two principal IDs in ascending order, then re-read credentials, proofs, link state and session ownership before committing. An already confirmed identical pair is idempotent. A different active pair is a conflict with a generic response. Never write an alias into memberships, reassign Telegram IDs, move owner foreign keys, or grant access by supplied organization ID.
- For a Telegram user adding their first password, the email identity can be created on the same principal after email proof and fresh Telegram proof. Keep explicit Web organization and Telegram source scopes even when the numeric principal matches. A revoked connection disables Telegram-to-Web sign-in for that co-resident principal while keeping the bot functional, and removes the email session's Telegram archive scope. A new unlinked Telegram web workspace on the same owner is deferred until source scopes can be enforced end to end.
- For a Web user adding a Telegram identity with no stored Telegram user, B1a presently disallows even `NULL → Telegram id`. Do not create an empty bot user merely to satisfy linking. LINK-01 must admit a capability-checked one-time attachment in one transaction with identity creation and the link grant, while keeping every non-null Telegram ID immutable. It may ship only with the co-resident unlink fences described above. If the bot has already materialized a Telegram principal through genuine use, preserve both principals and use the bilateral link. These are separate transition paths, with no heuristic merge.

## Credentials and session contract

- Canonical email input is ASCII, including A-label domains, with a lowercase local part and domain and a 254-character maximum. Reject raw Unicode, control characters, quoted forms and whitespace inside the address. Do not remove plus tags or dots. Applications must use the same normalization for registration, login, verification, recovery, and linking. The verified external identity owns the address. The credential table stores one Argon2id PHC string per canonical identity and no copy of its user ID.
- Pending registration is email proof only. A password submitted before proof must not become usable by a different browser clicking an unsolicited verification link. Bind verification to initiation, require the browser challenge and a password supplied by the verifying user before activation, and expire unused attempts. Create the verified identity, credential and personal organization/default project together, using existing B3/B4 provisioning. Do not generate a Telegram identifier or copy a Telegram brand for email-only registration. An empty default project has no completed brand.
- Tokens are random, purpose-specific, hashed at rest, one-use and TTL-limited. Keep separate registration, resend, recovery and linking lifecycles. Safe GET only displays the screen. Use explicit POST with Origin/Fetch Metadata checks and the existing host-only session cookie / CSRF boundary. Password verification uses Argon2id with bounded input and configured cost, and a dummy verification for absent identities. Recovery responses and registration initiation do not expose account existence. Enforce IP and per-account limits before expensive work or email delivery. Redact credentials, secrets, mail URLs and addresses from security logs.
- Rotate the web cookie on sign-in and sensitive changes; password reset revokes sessions owned by that credential principal, including any session with a cached linking grant. Resolve link scope afresh with the resource read, keeping reauthentication proof separate from CSRF. Email confirmation and recovery are delivered through a server-side mail adapter and disabled until real production delivery is proven. Tests use an isolated mail transport.

## Authorization and compatibility map

| Current boundary | AUTH/LINK change and invariant |
| --- | --- |
| B1a `IdentityService`, composite Telegram identity FK, immutable Telegram ID | Identity resolution returns the credential's original owner. Linking checks both proofs and introduces a separate grant. Verified signs of account control are never inferred from profile data. |
| B2 `web_auth`, `web_security`, `web_me` | Reuse cookie/session lifecycle and CSRF. Expose logical access and available verified methods without Telegram actor IDs. Revoke affected sessions and active context on unlink. Telegram polling remains bot-authenticated. |
| B3/B4 `organizations`, `memberships`, projects, brands | Use the exact resource owner and live membership check. Cross-channel discovery initially includes the linked principal's personal organization only, with scoped read and select rights. Team membership and writes do not transfer through an alias. Preserve versions and author/source fields. |
| `ProjectHistoryService`: runs, tasks, artifacts, saved results, project sessions | Resolve the exact verified Telegram actor server-side; reuse bounded queries with source kind and immutable ID. All detail, artifact and result reads must repeat the ownership/retention check in the request transaction. No provider call. |
| `conversations`, `messages`, delivery and receipts | Validate the proper `tg:<id>` or admitted scoped key grammar derived from the verified source. Never match arbitrary prefixes or combine by title/text. Receipts and internal debugging metadata are not exposed by default. |
| Telegram `ProjectContextService`, brand profiles and admission | Preserve Telegram's request IDs, ACK and author. A Web brand is a separate, explicitly selected, versioned source. Recheck grant and project on each new operation; check the selected brand's readiness server-side. No fallback or field mixing with the legacy brand. |

Link previews use counts and source categories only. Persist purpose, origin, expected recipient, expiry and proof bindings with each challenge. Confirm checks both proofs, an unconsumed attempt, fresh reauthentication and the current session in a single transaction. Unlink requires recent proof, keeps at least one verified usable sign-in for each affected logical workspace, revokes cross-access, and invalidates affected sessions and brand selections. Background jobs already admitted retain their original owner. Future B5/B6 threads are outside this contract.

## Migration and rollout

AUTH-01 expands the schema with credentials and records executable compatibility fixtures. AUTH-02 adds the proof lifecycle and disabled maintenance endpoints. AUTH-03 switches normal web entry to email-first after verified delivery and recovery exist. LINK phases add explicit grants and cross-channel projections independently. Before any production migration, verify a backup and rollback by restoring it in isolation. Operational rollback uses prior images and disabled flags while keeping additive schema. Refuse downgrade of any populated credential/link store. No credentials or linking flags are enabled by this migration.
