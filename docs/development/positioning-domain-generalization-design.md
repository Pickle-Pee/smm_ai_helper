# Обобщение стратегии на любые предметные области · документ решения

Статус: **решения владельца приняты** (15.11.2026, см. §9). Реализация идёт отдельными PR, этап 1 первым.
Production: `c6c5dc5` (CMO wire v13). Журнал приёмки: `acceptance-progress.md`.

## 1. Что показала приёмка

| Прогон | Где | Ветка стратегии POSITIONING | Итог |
| --- | --- | --- | --- |
| Курс «Призма», керамика «Тихая глина» (×6 релизов) | live harness | вручную написанные профили `photography` / `ceramics` | механика и содержание PASS |
| Курс, e99 / a602 / 6df396a / c6c5dc5 | Telegram | общий шаблон «освоение новой практики» | 1 подмена продукта, 3 отказа CMO |
| Пекарня (второй домен) | Telegram | общий шаблон «освоение новой практики» | механика PASS, **содержание FAIL** |

- Профили в `positioning_strategy.py` (коммит `eaaadd3`) включаются только при точном совпадении
  с текстами приёмочных сценариев (`_COURSE_TRUTH`, `_CERAMICS_TRUTH`, `_PHOTOGRAPHY_IDENTITY`).
  Курс из Telegram (условия через «;», с маленькой буквы) их уже не включает.
- Для всех остальных продуктов стратегический текст POSITIONING — это закрытые шаблоны,
  в которых зашита образовательная семантика: «освоение новой практики», «знакомство с новой
  практикой», «применение навыков», «что получает участник после курса». Модель только выбирает
  ключ шаблона, а текст рендерит сервер. Пекарня получила категорию «освоение новой практики».
- **Вывод:** live-гейт (курс + керамика) мерил код, до которого реальные пользователи не доходят.
  Критерий handoff «независимость от предметной области, без подгонки под обучающий пример» не выполнен.

Сопутствующие находки:
- CMO `strategic_bets`: условия владельца с цифрами («18:00») не попадают в SOURCE-каталог
  (`has_numeric_quantity`), поэтому структурный выбор ставок отключается. Модель написала свободный
  пункт `audience_understanding_ru` — это утечка технического ключа схемы, и проверки её пропустили.
- В CMO встречаются тексты, состоящие из одного слова `RECOMMENDATION` / `HYPOTHESIS`.
- Проверки CMO по словарю (демо, отсутствие оборудования, формат обратной связи) написаны под курс.
  Демо-класс закрыт в v13; класс «оборудование» по-прежнему валит Telegram-курс
  (`012fa4b7`, фрагмент условия через «;»).
- EXPERIMENTS в пекарне шёл 91,8 с при `HTTP_TIMEOUT=120` (риск обрыва, ср. ReadError на 91,5 с).

## 2. Почему так получилось

Цепочка решений Codex v5→v11 была рациональной: свободный текст POSITIONING выдумывал свойства продукта
(онлайн-формат, гончарный круг, домашние задания, помощь мастера). Каждую утечку закрывали сужением:
сначала закрытыми ключами источников, затем серверными шаблонами, затем профилями под конкретные тексты.
Проверка фактов стала надёжной, но содержание перестало зависеть от продукта, а релизный гейт этого
не замечал, потому что использовал те же два текста, под которые написаны профили.

## 3. Ограничения, которые сохраняются при любом варианте

- Условия владельца (RTB, offer) — только дословно через SOURCE; фрагменты, теряющие оговорки, запрещены.
- Гипотеза не выдаётся за факт; не выдумываются свойства продукта, гарантии, числа, доставка, форматы.
- Durable POSITIONING verification, receipts, fencing и fail-closed не ослабляются; без автоповторов.
- Существующий оркестратор, Module Registry, Quality Gates и канонический формат хранения v1 сохраняются.

## 4. Варианты для стратегического текста POSITIONING

### A. Нейтральные шаблоны от продукта и аудитории

Переписать общий шаблон без образовательных слов и параметризовать его текстами владельца, например:
«Предлагаем проверить, к какой категории аудитория «{target}» относит «{product}»»;
«Гипотеза: при выборе «{product}» аудитория сравнивает варианты по ясности условий: «{owner terms}»».

- Плюсы: быстро; фактическая безопасность прежняя; работает для любого домена.
- Минусы: позиционирование превращается в набор исследовательских вопросов без маркетинговой идеи;
  ценность для пользователя низкая. Профили под тесты всё равно нужно убрать.
- Стоимость: 1 цикл (около 8 POST harness + выкладка + Telegram).

### B. Гипотезы пишет модель, факты проверяет существующая независимая верификация (рекомендую)

Для «рыночных» гипотез (category, frame_of_reference, demand_context, JTBD_frame, points_of_parity,
differentiation, USP_directions) модель снова пишет короткий текст сама: тип строго HYPOTHESIS, без
утверждений о свойствах продукта. RTB, offer, target и positioning_statement остаются серверными: SOURCE и шаблон
с подстановкой текстов владельца. Дополнительно:
- провайдерская схема запрещает в этих полях словарь свойств и форматов (подход v13: онлайн-формат,
  домашние задания, персональный разбор, доставка, гарантии, числа и т. п.);
- текст проходит существующую независимую верификацию POSITIONING (атомарный аудитор) и обычные
  детерминированные проверки; при отказе публичный артефакт не создаётся (как сейчас).

- Плюсы: содержание зависит от продукта и рынка; защита от выдумок многослойная — схема, аудитор
  и детерминированные правила. В v5–v9 аудитора ещё не было.
- Минусы: вернётся часть ложных отказов верификации; нужна измеримая проверка на нескольких доменах
  до релиза. Это заметная работа (схема, инструкции, тесты, offline-реплеи).
- Стоимость: 2–3 цикла с замером (оценочно 20–30 POST на гейт с несколькими доменами).

### C. Гибрид: B с детерминированным откатом на A для отдельных полей

Как B, но если аудитор отклоняет конкретное рыночное поле, сервер подставляет для него нейтральный
шаблон из A (без нового provider call) и помечает поле как «гипотеза не прошла проверку».

- Плюсы: граф почти всегда завершается, пользователь получает лучшее из доступного.
- Минусы: меняет правило «отказ верификации = нет артефакта»; нужно явное согласие владельца
  и отметка в UI.

## 5. Сопутствующие изменения (при любом варианте)

1. **Убрать профили под тестовые тексты** (`photography`, `ceramics`, `source_fact_units` по точному тексту)
   или обобщить их; иначе тесты продолжат проходить «по совпадению».
2. **CMO ставки с числами:** разрешить в SOURCE условия владельца с числами (они рендерятся дословно
   из источника и не являются вычислением) либо включать закрытый выбор ставок без SOURCE.
3. **Утечки ключей и пустые тексты:** декодер отклоняет свободные пункты, совпадающие с ключами схемы
   (`*_ru`, `*_en`, `HYPOTHESIS`, `RECOMMENDATION`); схема требует содержательный текст.
4. **Класс «оборудование» в CMO:** закрыть так же, как демо в v13 (запрет в свободной прозе,
   условие только целиком через SOURCE, закрытый план «привести полное условие владельца»).
5. **Таймаут EXPERIMENTS:** увеличить бюджет HTTP для EXP (например, до 180 с) или уменьшить объём
   вывода; отдельно от логики содержания.

## 6. Новый релизный гейт (обязательно)

- Live harness на ≥4 доменах, минимум 2 не-образовательных (пекарня, B2B-услуга), плюс курс и керамика.
- Входы в формате Telegram: условия одним предложением через «;», как их извлекает проекция,
  а не заранее нарезанные факты.
- Детерминированный тест обобщения: для набора не-образовательных продуктов ни один шаблон
  и ни одна закрытая формулировка не содержит образовательной лексики (курс, обучение, практика, навык, участник).
- Рубрика разбора содержания включает «соответствие предметной области», а не только фактическую безопасность.

## 7. Решения, нужные от владельца

- **D1.** Вариант для стратегического текста POSITIONING: A, B или C.
- **D2.** Допустим ли откат отдельного поля на нейтральный шаблон с пометкой в UI (нужно для C)?
- **D3.** Бюджет платных вызовов на новый гейт с несколькими доменами (оценка 20–30 POST за прогон гейта).
- **D4.** Порядок: сначала сопутствующие исправления 5.2–5.5 (быстро, закрывают Telegram-курс),
  затем вариант по D1 — или всё одним циклом.

## 8. Рекомендация

D1 = **B**, D2 = нет на первом этапе (отказ остаётся отказом), D4 = два этапа:
1. Быстрый этап: 5.1 (убрать профили) + 5.2–5.5 и нейтральный A как временная замена общего шаблона;
   новый гейт из §6. Это сразу убирает «освоение новой практики» у пекарни и закрывает текущие
   причины падения курса.
2. Основной этап: B для рыночных гипотез с замером на нескольких доменах до выкладки.

## 9. Решения владельца (15.11.2026)

- **D1 = B** как целевая архитектура: рыночные гипотезы (category, frame_of_reference, demand_context,
  JTBD_frame, points_of_parity, differentiation, USP_directions и др.) пишет модель; факты о продукте,
  offer и RTB остаются строго source-bound.
- **D2 = нет.** Отклонённое поле не подменяется нейтральным шаблоном. Fail-closed, durable verification,
  receipts, fencing и Quality Gates сохраняются.
- **D3:** первоначально 20–30 платных POST на многодоменную приёмку; расширение — только после отчёта
  о причинах и результатах предыдущих вызовов. Неизвестные или завершённые provider operations не повторяются.
- **D4:** два этапа.
  1. Этап 1: убрать привязку к тестовым текстам, заменить образовательный fallback нейтральным,
     исправить SOURCE с числовыми условиями, утечки технических ключей, защиту условий оборудования;
     по EXPERIMENTS сначала диагностика ReadError и бюджета времени графа, затем предложение по таймауту.
  2. Этап 2: B с независимой верификацией стратегических гипотез и многодоменной приёмкой.

Дополнительные требования владельца:
- B — не очередной набор предметных regex, а архитектурная граница «подтверждённый факт /
  рыночная гипотеза / рекомендация». Метка HYPOTHESIS не разрешает неподтверждённые свойства продукта
  или ложные утверждения о рынке.
- Условия владельца сохраняются полностью; разбиение по «;» и SOURCE-каталог не теряют оговорок.
- Исправление SOURCE с числами не разрешает произвольные числовые заявления.
- Гейт: ≥4 предметные области, ≥2 необразовательные, реальные формулировки из Telegram и отдельный
  ранее не использованный контрольный сценарий. Критерий — содержательная стратегия без выдумок,
  отраслевых подмен и шаблонной воды, а не только техническое прохождение.
- При отказе верификации исследуется конкретная причина; ограничения не ослабляются.
- Каноническое хранение v1, оркестратор и гарантии идемпотентности не меняются.
- Отдельные reviewable PR; сначала offline и CI, затем контролируемая live-приёмка; без автодеплоя.
